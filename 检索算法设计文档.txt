检索逻辑：

一、怎么定性文档类型

只看 structure_index 的 token 估算。

structure_tokens <= 6000
-> compact_structure

6000 < structure_tokens <= 20000
-> paged_structure

structure_tokens > 20000
-> filtered_or_paged_structure

如果超过 6000 token，按顶层 node 分批：

{
"document_structure_mode": "paged_structure",
"structure_tokens": 14300,
"part": 1,
"total_parts": 4,
"structure_index": [
    {
    "node_id": "frontmatter",
    "title": "合同首部",
    "summary": "..."
    },
    {
    "node_id": "body/sec_001",
    "title": "第一条 合同内容",
    "summary": "..."
    }
]
}

agent 如果当前 part 没有相关内容，再请求：

{
"tool": "get_document_structure",
"part": 2
}

1. Node Token 阈值

不要照搬 PageIndex 的 20000。你的 DOCX 合同审查需要精确定位和计算，所以 node 应该更小。

建议：

node_target_tokens: 700
node_soft_limit_tokens: 1000
node_hard_limit_tokens: 1800

含义：

参数    含义
━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
700     理想子 node 大小
──────  ──────────────────────────────────────────
1000    超过后优先尝试继续按子标题/编号拆
──────  ──────────────────────────────────────────
1800    超过后必须拆，即使没有标题也按段落聚合切

2. 累加加载思路

不是一次把所有原文塞给 LLM，而是：

先给结构树 summary
agent 选中候选 node
系统加载候选 node 原文
如果不够，再累加加载相关 node

累加顺序建议固定：

第 1 层：命中的 node
第 2 层：命中 node 的 children
第 3 层：命中 node 的前后 sibling
第 4 层：命中 node 的 parent
第 5 层：被规则命中的交叉引用 node，例如“详见附件”

3. 什么时候继续累加

只保留这几个判断：

命中 node 太短：< 80 tokens
命中 node 太长但有 children：先展开 children，不直接塞父 node
审查要素不完整：例如付款审查缺总价/付款明细/发票/维保尾款
出现引用：详见附件、见清单、另行约定
模型返回“信息不足”
