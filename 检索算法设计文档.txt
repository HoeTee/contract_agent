1. 段落顺序这里的 word/document.xml w:body 直接子节点 是什么意思？你是要重新建立一个索引吗 还是 建立一个标号系统 我想知道这个新的索引或标号是怎么实现的

答：这里不是替换 Word 原生结构，也不是只做一个简单编号系统，而是在 Word 原始 XML 阅读顺序上建立一层“结构化索引”。`word/document.xml` 里的 `w:body` 是正文容器，它下面的直接子节点通常是 `w:p` 段落和 `w:tbl` 表格。我们按这些直接子节点的出现顺序生成稳定的内部 anchor，例如 `p_0001`、`tbl_0001`、`p_0002`。这个 anchor 是程序自建的，用于检索、node 边界、批注定位回溯。实现上是遍历 `w:body` 的直接 children：遇到段落就分配一个递增的 `p_xxxx`，遇到表格就分配一个递增的 `tbl_xxxx`，同时保存该 child 在 XML 中的引用、纯文本、样式、页码估计和所在 node。

2. 附件内布视觉标题判断 是怎么实施的

答：附件内部视觉标题判断只用于没有可靠 `outlineLvl` 的场景。实施方式是先限定范围：只在某个正式附件 section 内扫描段落，不在全文任意位置扫描。对每个候选段落提取 DOCX 样式信号：文本长度、是否居中、run 加粗比例、最大字号、前后空段、后续若干 body child 是否出现正文/编号标题/表格。然后按规则打分，达到阈值才认为是附件内部标题。这个逻辑模仿 PageIndex 利用版式信号识别标题的思想，但数据来源是 DOCX XML，不是 PDF OCR/版面解析。

3. lastRenderedPageBreak 是在哪个 xml 文件里？document.xml 里不存在

答：`lastRenderedPageBreak` 如果存在，位置就在 `word/document.xml` 的正文 run 内，常见形态是 `<w:lastRenderedPageBreak/>`。如果你在某个 `document.xml` 里没有看到，说明该 DOCX 没有保存 Word 上次渲染分页结果，或者该文件被生成/清洗时没有写入这个标记。因此页码字段必须是可选字段：存在时估算页码，不存在时 `page_start/page_end=null`，不能把页码作为强依赖。批注定位仍然依赖 `p/tbl anchor + quoted_text`。

4. node confidence level 改为计数吧 目前的 high medium 不具备量化意义

答：同意。`high/medium/low` 可以作为展示层结果，但底层应该保存数字化证据。建议改成 `confidence_score` 和 `confidence_evidence` 两个字段。例如：编号形态命中 +2，编号连续性 +3，direct outlineLvl +4，style outlineLvl +3，视觉标题得分 +0 到 +4，附件上下文命中 +2，排除规则命中 -5。最终根据分数映射展示等级，但判断和调参都以数字为准。

5. “表格单元格内的标题文本” 不属于bodynode吗 表格内容当然属于正文的一部分 只不过不是章节标题罢了

答：你的理解是对的。表格当然属于 BodyNode 的正文内容。原文里“不属于 BodyNode”的表达应修正为：表格单元格内文本不参与“正文章节标题层级”的识别，不作为切分 Level1/Level2/Level3 section 的标题候选。表格本身应作为 `TableNode` 挂在当前 section/node 下，并保留 `tbl_xxxx` anchor。也就是说，表格属于正文内容，但表格内部标题不提升为正文结构树章节标题。

6. tailnode 的辨识逻辑能够优化吗 比如通过 附件子标题来辨识？有些合同文本正文不存在“以下无正文”“以下为合同签署栏”，而且bodynode 怎么与 tailnode 进行区分的？这一块区分的逻辑不清晰

答：可以优化，而且不能只依赖“以下无正文/签署栏”。建议把 TailNode 识别改成多信号边界判断：第一，最后一个正式正文 Level1 section 之后的连续内容进入尾部候选；第二，出现签署、盖章、法定代表人、授权代表、日期、开户信息等签署页信号时提高尾部得分；第三，如果后续出现正式附件 section，则附件开始位置之前的签署/空白/说明内容归 TailNode；第四，如果没有尾部标记但正文 Level1 已结束且后续不再出现正文标题连续性，也可以形成低置信度 TailNode。BodyNode 与 TailNode 的边界不靠单个关键词，而靠“最后一个正式正文 section 结束位置 + 签署页信号 + 附件起点”共同确定。

7. 一切等级的参数最好都设置成数字变量

答：同意。所有影响判断的等级都应数字化，展示层再映射成文字。建议统一使用：`score` 表示置信分，`threshold` 表示触发阈值，`limit` 表示 token/字符预算，`window` 表示扫描窗口。例如 `visual_title_min_score=2`、`main_title_min_score=5`、`attachment_section_min_score=4`、`tail_min_score=3`、`node_soft_limit_tokens=1000`。这样后续可以通过样例统计调参，而不是在代码里散落 `high/medium/low`。

9. chunknode 生成的逻辑没有介绍

答：ChunkNode 的生成逻辑应补充为：当一个结构 node 超过 token 阈值，先尝试按更细编号或视觉子标题切分；如果没有可靠子标题，则按 `w:body` child 顺序把连续段落和表格聚合成 chunk。目标大小是 `node_target_tokens=700`，超过 `node_soft_limit_tokens=1000` 尽量收口，超过 `node_hard_limit_tokens=1800` 必须切。表格不拆散，作为一个整体放入当前 chunk；如果单个表格自身过大，则单独形成 `TableNode` 并标记 `oversized=true`。chunk 之间可以有少量 overlap，例如 80 tokens，用于避免上下文断裂。

11. node 字段设计字段值是不是太多了？这个远比 pageindex 复杂，看起来会浪费过多 token，pageindex 每个 node 似乎只有 四个字段（我不是说只需要四个字段，但是那么多字段的必要性是什么）

答：字段确实需要分层，不能全部输出给 LLM。完整 node 字段是内部索引字段，用于构建、调试、检索、批注和回溯；输出给 LLM 的应是轻量视图。建议拆成三种视图：`storage_node` 保存完整字段，`structure_view` 只输出 `node_id/title/summary/page/token_estimate/children`，`content_view` 在展开原文时输出 `node_id/title/text/anchors`。这样内部可以比 PageIndex 多保存 DOCX anchor、XML 原生 ID、置信证据等字段，但不会浪费 LLM token。

12. 结构树需要给 LLM 一个低 token 的总览。 这个是 summary 的生成逻辑吗

  结论：完整修改方案是把当前 DOCX 检索工具改成 PageIndex-like 两阶段架构：

  第一阶段：structure_tree.json 给 LLM 选 node / anchor range
  第二阶段：根据 node_id 或 start_index/end_index 从 content_store.json 取原文
  批注定位：根据 anchor_store.json 回到 DOCX XML

  不是做“逐级下钻”，也不是按 page，而是用 node + anchor range 替代 PageIndex 的 page range。

  六、检索流程改造

  当前 ask 应改成：

  读取 document_index.json
  -> 找到 structure_tree.json
  -> 输入 structure_tree["structure"] 给 LLM
  -> LLM 返回 node_id/start_index/end_index
  -> 从 content_store.json 取 text
  -> 返回统一 nodes 列表

  返回结构简化为一个字段：

  {
    "query": "...",
    "nodes": [
      {
        "node_id": "body/sec_002",
        "title": "第二条 合同金额及支付方式",
        "text": "...",
        "start_index": 51,
        "end_index": 67,
        "start_anchor": "p_0051",
        "end_anchor": "p_0067",
        "source": ["structure", "vector"],
        "truncated": false
      }
    ],
    "elapsed_seconds": 12.3
  }

  不再对用户暴露：

  structure_matches
  vector_matches
  ranked_matches
  content_context
  pagination
  budget

  这些只写入 log。

  七、向量补召回

  向量索引不另建位置体系，只返回 node_id。

  metadata 使用：

  {
    "node_id": "body/sec_002",
    "title": "第二条 合同金额及支付方式",
    "summary": "...",
    "start_index": 51,
    "end_index": 67,
    "node_type": "body_section"
  }

  合并逻辑：

  structure 召回 node_id
  vector 召回 node_id
  -> 按 node_id 去重
  -> rerank
  -> 从 content_store 取 text

  八、超阈值节点处理

  不是所有大节点都要拆。规则改成：

  如果结构树节点过大：
    结构树按 PageIndex 方式顺次分批

  如果取出的 content text 过大：
    先看该 node 是否有 nodes 子节点
      有：优先展开子节点内容
      没有：按 anchor 顺序切 chunk

  body 这种区域大不是问题，因为最终不应该取 body.text 作为审查上下文。
